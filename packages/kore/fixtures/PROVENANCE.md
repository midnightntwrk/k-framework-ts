# Fixture provenance

Every file here is **byte-for-byte what the upstream repositories carry**,
except the explicitly identified `ambiguity/` pattern extraction — none is
hand-authored. This package is a hand-transcription of upstream
KORE sources, and a hand-transcription is not self-verifying; these fixtures
are the evidence. `SHA256SUMS` (in this directory) records a checksum for every
fixture file; regenerate with the command at the bottom of this document.

## `parser/` — the reference parser suite (196 files)

From `haskell-backend:test/parser/`: all 98 `.kore` inputs and their 98
`.kore.golden` files. Upstream, the golden is **the stderr of
`kore-parser --no-print-definition`** (see `test/parser/Makefile` there) — so
this corpus is a positive *and* negative oracle at once:

- **72 empty goldens** — the input parses and verifies; our parser must accept
  it, and text round-trip (parse → write → reparse → equal) must hold.
- **26 non-empty goldens**, in two distinct classes a consumer of this corpus
  must not conflate:
  - Goldens matching `^<file>.kore:<line>:<col>: unexpected …` are **lexical or
    parse errors**. Our parser must reject the input; the `line:col` is
    assertable (we do not chase the exact message text, which names Haskell
    token constructors like `TokenSort`).
  - Goldens beginning `Error:` followed by module/declaration prose are
    **semantic-verification errors** (e.g. "Expected 0 sort parameters, found
    1", "missing hook attribute"). These inputs are *syntactically valid*: our
    parser must **accept** them, because this package does not implement the
    validity rules (§Validity of `kore-syntax.md`). If a validity checker is
    ever added, these goldens are its ready-made suite.

Note: pyk (`k/pyk/src/tests/unit/kore/test-data/definitions/`) carries a copy
of this same suite, but it has **drifted** from the haskell-backend original
(observed: different `\and`/`\or` nesting arity in the JSON companions, and a
different pass/fail split). We deliberately vendor the haskell-backend
originals — they sit next to the reference parser that defines the format.

## `json/` — reference-codec KORE-JSON goldens (41 files)

40 files from `haskell-backend:test/parser/json/`, named after their `.kore`
counterparts in `parser/`. Each is a JSON **array** of KORE-JSON documents
(`{"format": "KORE", "version": 1, "term": …}`). Per the upstream
`test/parser/json/README.md`, they are generated by the reference Haskell
codec's own round-trip test (`Test.Kore.Syntax.Json.Roundtrips.makeGold`) —
i.e. these bytes are what `Kore.Syntax.Json` itself emits. That makes them
cross-implementation conformance fixtures: our decoder must read them, and
decode(golden) must equal decode(encode(decode(golden))).

Plus `assoc.json`, the one file pyk **adds** to its copy of this corpus
(`k/pyk/src/tests/unit/kore/test-data/json/assoc.json`): it covers the
`LeftAssoc`/`RightAssoc` JSON tags, which the 40 upstream files do not
exercise. pyk's copies of the other 40 were **not** taken (see the drift note
above).

## `patterns/` — bare-pattern inputs (4 files)

## `ambiguity/` — frontend GLR evidence (1 file)

`llvm-amb-rule.kore` is the pattern on lines 412–413 of
`runtimeverification/llvm-backend:test/defn/amb.kore` at the exact gitlink
commit above (source-file sha256
`5a063d11a7f4aeae0bf3dc424002af4a368ef6ce861565b66cabdf0c3357b91d`). It
contains the frontend's real `Lblamb{SortExp{}}` application underneath an
`inj`, as used by the LLVM backend's own ambiguity definition test. The fixture
is a deliberately narrow extraction so it can be read as one `Pattern`: four
spaces of enclosing alias indentation and the alias declaration's trailing
`[]` are removed. It is not presented as a complete generated parser output.

It was extracted on 2026-08-07 from the repository root. The operation is
platform-independent; `curl`, `sed`, and `sha256sum` are the only tools. K was
identified as v7.1.337 (build date 2026-08-06), whose nested gitlink resolves to
the commit above. The exact command is:

```sh
curl -fsSL \
  https://raw.githubusercontent.com/runtimeverification/llvm-backend/f02284f09858cd2b9f310ad0142b3e04054295ec/test/defn/amb.kore \
  | sed -n '412,413p' \
  | sed -e 's/^    //' -e 's/ \[\]$/' \
  > packages/kore/fixtures/ambiguity/llvm-amb-rule.kore
sha256sum packages/kore/fixtures/ambiguity/llvm-amb-rule.kore
```

The expected fixture sha256 is
`5783ee32cd85d6fc44e9a7be79fde17cba66922bae87e3a9b96c40ca04eca641`.
Ordinary CI only consumes the checked-in pattern and byte-checks
`fixtures/SHA256SUMS`; it does not contact GitHub or regenerate the excerpt.

The behavioral claim is separately watched through content-tier source pins:
`k-distribution/include/kframework/builtin/kast.md` (sha256
`42c815ea80ed522dde962e231bdacc3d0d7e643016f8d649eab8d4be1d570040`) declares
`amb`, and `k-distribution/include/kframework/cparser/main.c` (sha256
`27b4e784542a732a7cb3699f6b78f1e25500ec38a8eae22bc1c05faa83a27201`) emits
binary `Lblamb` nodes. `check-k` reports drift in either as advisory content
drift; re-run the recorded source extraction or a GLR parser before changing
the projection.

## `kore-schema.json`

From `haskell-backend:src/main/json/kore-schema.json`, unmodified: the

## Formatter exclusion

The workspace `.oxfmtrc.json` and `.oxlintrc.json` ignore every `fixtures`
directory by that bare pattern, so nothing here can be reformatted by
tooling. (kast-json's PROVENANCE records the incident that motivated this.)

## Regenerating the checksum manifest

```sh
cd packages/kore/fixtures
sha256sum $(find . -type f ! -name SHA256SUMS ! -name PROVENANCE.md | sort) > SHA256SUMS
```
