# Fixture provenance

Two kinds of bytes live here, and the distinction is the whole point of this
file.

- **`upstream/` and `src/`** are byte-for-byte what the `k` repository has
  committed. Nothing was reformatted, re-indented, renamed inside, or trimmed.
- **`definitions/` and `derived/`** are **our toolchain's output**, not files
  upstream ever committed. Upstream has no committed `compiled.json` for these
  definitions and no committed KAST for three of the four KORE→KAST goldens;
  the reason is that pyk's `konvert` suite kompiles at test time, and the
  `regression-new` expected side is *pretty-printed K*, not KAST.
  We manufacture them once so the tests can run with no K install and no network.

The `definition.kore` / `compiled.json` side is still a genuine **third-party
oracle** — it is the Java frontend's output, not pyk's and not ours — which is
what makes the arrangement worth the caveat.

The `fixtures` directory is excluded from the formatter by the repo-root
`.oxfmtrc.json` `ignorePatterns`. Verified for this directory:
`oxfmt --check packages/konvert/fixtures` reports *"All matched files may have
been excluded by ignore rules."* Read
`packages/kast-json/fixtures/PROVENANCE.md`'s opening section for what happens
when that is not true.

### `module-to-kore/*.k` — not vendored, but the recipe is measured

The 9 upstream `module-to-kore/*.k` files are deliberately **not** vendored:
`moduleToKore` is not implemented here (`README.md` says why). The recipe is
recorded anyway, because the result behind it took a real toolchain run and is
not re-derivable by reading:

**No committed golden exists anywhere** — not in `k/` (there is no
`ModuleToKORETest`; the `KOMPILE_BACKEND=kore` regression dirs `rm -f
$(DEF).kore` in `clean` and diff nothing, so the test passes iff `kompile` exits
0), not in haskell-backend, not downstream. **But it can be manufactured
offline, and that was verified**: kompiling 7 of the 9 files with the same
v7.1.337 toolchain used for `definitions/`, and re-implementing
`test_module_to_kore.py`'s comparison — drop `symbol'Kywd'` attributes,
canonicalise `SortDecl` variables to `SortS{i}`, skip rule axioms:

```
empty hook overload syntax-sort impure format frontend-only
  → name_eq=True attrs_eq=True MISSING=0 EXTRA=0     (7/7)
```

That is a genuine **third-party** oracle: the expected side is
`ModuleToKORE.java`'s output, not pyk's. It costs ~4.5 MB of `compiled.json`
plus ~1.4 MB of `definition.kore`; a 2.5 MB subset (`empty`, `hook`,
`overload`, `syntax-sort`) still covers sort declarations, hooks, overload
axioms and `syntax sorts`. Two of the nine need attention: `anywhere.k` fails
with _"anywhere is not supported by the haskell backend"_ (retry
`--backend llvm`, or drop it and lose all `AddAnywhereAtts*` coverage), and
`coverage.k` needs `--coverage`.

The three normalizations are not pragmatism — byte-identical `definition.kore`
output is unreachable **in principle**, so a sort-order diff must never be
treated as a bug to fix. `SortHead.compare`
(`k-frontend/src/main/scala/org/kframework/kore/interface.scala:154-157`)
compares `this` against `this`; `that` is never read, so it returns 0 for every
pair, `sortedDefinedSorts` is a stable sort under an always-equal comparator,
and `sort` declarations emit in Scala hash-trie order — deterministic for
identical input, unreproducible from semantics. `README.md` carries the same
finding for the same reason.

### Why both backends are here

This is a correction worth recording rather than silently resolving. pyk's test
kompiler does **not** default to the haskell backend: `KompiledTest` leaves
`KOMPILE_BACKEND = None` (`pyk/src/pyk/testing/_kompiler.py:100`), and
`Kompile.from_dict` reads that as **llvm** —
`backend = KompileBackend(dct.get('backend') or 'llvm')`
(`pyk/src/pyk/ktool/kompile.py:243`). Neither `test_simple_proofs.py` nor
`test_cell_map.py` overrides it. So the definition those 106 upstream cases
actually run against is the **llvm** one.

And the two are not interchangeable. Measured on `simple-proofs.k` at this
toolchain, the `compiled.json` module sets diverge:

```
haskell: 67 modules      llvm: 60 modules
only haskell: BOOL-KORE BYTES-STRING-ENCODE BYTES-SYMBOLIC-CEIL INT-KORE
              INT-SYMBOLIC INT-SYMBOLIC-KORE K-EQUAL-KORE STRING-KORE
only llvm:    BYTES-CONCRETE
```

Both are therefore vendored. The unsuffixed name is the haskell build (it is
what was handed off first and what the `konvert` transcription work started
against); `*.llvm.compiled.json` is the pyk-default build. **If a transcribed
case from `test_simple_proofs.py` or `test_cell_map.py` disagrees with the
haskell fixture, re-run it against the `.llvm.` fixture before treating the
disagreement as a transcription bug.**

## `derived/` — the expected KAST for the four KORE→KAST goldens

The wrinkle: the *committed* expected side of
these directories is pretty-printed K (`KAST_FLAGS=--input kore --output pretty`
in three of the four `Makefile`s), and we have no pretty-printer. So the
expected KAST is re-derived locally.

Each definition was kompiled with the backend and flags its own `Makefile`
names, in `<scratch>/regr/<dir>/`:

```
$ cd <scratch>/regr/issue-2356-koreDecode      && kompile test.k --backend haskell
$ cd <scratch>/regr/kast-kore-input            && kompile kast-in.k --backend haskell
$ cd <scratch>/regr/poly-unparsing             && kompile poly-unparsing.k --backend haskell
$ cd <scratch>/regr/issue-1682-korePrettyPrint && kompile test.k --backend haskell --syntax-module TEST
```

Then, from each of those directories, once per output format:

```
$ kast result.kore.kast                --input kore --output {kast,json} --definition test-kompiled
$ kast kast-in1.kast                   --input kore --output {kast,json} --definition kast-in-kompiled
$ kast kast-in2.kast                   --input kore --output {kast,json} --definition kast-in-kompiled
$ kast kast-in3.kast                   --input kore --output {kast,json} --definition kast-in-kompiled
$ kast test1.kore.kast --expand-macros --input kore --output {kast,json} --definition poly-unparsing-kompiled
$ kast 2.kast                          --input kore --output {kast,json} --definition test-kompiled
```

The `--definition <dir>` shape and the `--expand-macros` on `poly-unparsing`
come from `k-distribution/include/kframework/ktest.mak:111` and each directory's
`KAST_FLAGS`. All twelve invocations exited 0.

Both formats are produced. The `.json` is what the TS tests should read (it is
KAST-JSON v4, parseable by `@kframework-ts/kast-json` with no textual-KAST
parser); the `.kast` is kept because it is small, human-readable, and is the
form the upstream `Makefile` would compare.

| derived file                                       | bytes | derived textual KAST                                                   |
| -------------------------------------------------- | ----: | ---------------------------------------------------------------------- |
| `issue-2356-koreDecode/result.kore.kast.{kast,json}` | 377 / 1 459 | the five override-character labels, `#fail`, `?_0`, `_V_9`, `^-_<>&` |
| `kast-kore-input/kast-in1.kast.{kast,json}`        | 54 / 369 | `#Equals{Int,Int}(#token("3","Int"),#token("4","Int"))`                 |
| `kast-kore-input/kast-in2.kast.{kast,json}`        | 38 / 371 | `#Equals{Int,Int}(X,#token("4","Int"))`                                 |
| `kast-kore-input/kast-in3.kast.{kast,json}`        | 39 / 372 | `#Equals{Int,Int}(@X,#token("4","Int"))` — **the set variable survives** |
| `poly-unparsing/test1.kore.kast.{kast,json}`       | 70 / 338 | `#Ceil{Int,GeneratedTopCell}(...)` — a KLabel carrying sort params      |
| `issue-1682-korePrettyPrint/2.kast.{kast,json}`    | 25 / 205 | `pred1(#token("3","Int"))`                                             |

Two of these confirm claims made from source reading, now measured:

- **`kast-in3` round-trips `@X` as `@X`.** The KORE input is
  `\equals{SortInt{},SortInt{}}(@X:SortInt{},\dv{SortInt{}}("4"))` and the
  derived JSON holds `{"node":"KVariable","name":"@X",…}`. pyk would have
  produced `Var'-AT-'X`; Java is right, and this is the only committed fixture
  in the ecosystem that shows it.
- **`poly-unparsing` needs no `Lblite` special case.** The derived label is
  `#Ceil` with two sort params, i.e. the general mechanism, not the hardcoded
  symbol.

## Not vendored, and why

- **`module-to-kore/*.k` and its `definition.kore` golden** — deferred with
  `moduleToKore`; see above.
- **An expected KAST for `mir-semantics-295.json`** — needs the mir-semantics
  definition, a separate repository. Upstream's own test only times the
  conversion.

  This was tried, and it does not work — recorded so it is not tried again.
  `runtimeverification/mir-semantics` at `4d793252` builds cleanly with the
  toolchain above (`kompile --backend haskell --main-module KMIR
  --syntax-module KMIR-AST --md-selector 'k & ! concrete' --emit-json` on
  `kmir/src/kmir/kdist/mir-semantics/kmir.md`, 27 s, zero warnings), but the
  vendored term is from a **pre-rewrite** KMIR: its symbols name modules
  `MIR-SYNTAX`, `MIR-EXECUTION`, `MIR-BASICBLOCK-SYNTAX` and sorts like
  `FunctionCellMap`, none of which survive in today's `KMIR-AST` / `rt/`
  definition. **106 of the term's 112 KORE symbols have no counterpart** in the
  current one, so a definition-ful conversion would fail rather than produce an
  oracle. Upstream's term and upstream's semantics have drifted apart, and the
  intermediate mir-semantics that would match is not buildable at K `v7.1.337`.

- **A `compiled.json` for a real semantics** — measured and declined *here*
  specifically, not in general. KWasm's (4.9 MB) is vendored by
  `packages/wasm-fixtures`, a private package that owns that artifact for the
  whole workspace; its `fixtures/PROVENANCE.md` has the census that justified
  it and the licence position, which is **NCSA** — permissive, notice carried
  beside the bytes in that package's `THIRD-PARTY-NOTICES.md`. Committing a
  second copy here would put 9.8 MB of one definition in a tree whose whole
  fixture footprint is 8 MB, and what this soak actually needs is the
  **complete** directory — 6 MB of KORE more still.

  So `test/wasm-soak.test.ts` reads a **locally built** directory instead,
  found by `wasmSoakDir()` (`$KFRAMEWORK_TS_WASM_KOMPILED`, then a content-keyed
  cache), and skips when there is none. The recipe and the builder are in
  `packages/wasm-fixtures`; the build takes 21 s and needs no network. With it,
  `kastToKore`/`koreToKast` run over 3880 real rule sides instead of
  `simple-proofs`' 47, and `kruleToKore` over 2062 real rules instead of the
  handful in `rule.test.ts` — after asserting that the directory hashes to the
  same definition as the vendored `compiled.json`.

  Note what this is *not* an instance of. Fixtures are read across packages in
  this repository, fourteen times over; the convention is one **owning** package
  per fixture, which vendors the bytes and records their provenance, not that
  each package re-vendors what it reads.

- **A `kruleToKore` oracle against K's own `definition.kore`** — attempted and
  abandoned, with a number. Joining every rule to the axiom carrying the same
  `UNIQUE_ID` and comparing `koreText` gives **0 matches out of 1539**, because
  `_krule_to_kore` discards `UNIQUE_ID`, `Source`, `Location` and `Production`
  (`_kast_to_kore.py:309`) and emits `\equals{Bool,R}(true, true)` where
  `ModuleToKORE` emits `\top{R}()`. pyk is not reproducing the frontend, so
  there is no oracle here to have — which is consistent with upstream's own
  `frontend-comp-skip`, and is why the soak asserts a KORE-side fixed point
  instead.
- **Foundry `kast-to-kore/compiled.json`** (37 MB) — out-of-tree soak test.
- **The `regression-new` `.kore` files that go the other direction**, the
  haskell-backend `.k`+`.kore` pairs, the profiling `compiled.json` /
  `definition.kore` pair, and evm-semantics' `gst_to_kore` goldens — each ruled
  out on inspection: none of them pins anything the corpora above do not.
